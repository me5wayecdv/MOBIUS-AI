## 2026-11-15 · RL-010 · Migrations, and the test that makes them mean something

**Scope:** Alembic (`alembic.ini`, `migrations/env.py`, revision `0001`), `tests/test_migrations.py`,
ADR-025. Tests 313 → 319.

| # | Finding | Resolution |
|---|---|---|
| 1 | The test suite builds its database with `create_all`, so it would pass happily while the migrations drifted from the models | A test builds a database *only* with `alembic upgrade head` and then runs `alembic check`, which fails when a model change has no migration. Autogenerate is not the guarantee; the check is |
| 2 | The autogenerated revision id was `54d2379515ac`, so `upgrade head` logged a hash nobody can order by eye | Renamed to `0001`; the history is meant to be readable in a deployment log |

## 2026-11-15 · RL-009 · The first measurement, and what it says when it is bad

**Scope:** pinned corpus (7 public APKs), `scripts/fetch_corpus.py`, Wilson intervals in the
benchmark, `docs/BENCHMARK_RESULTS.md`. Tests 301 → 313.

**Result, in one line.** Precision 100 % (1/1, 95 % CI 20.6–100 %), recall 25 % (1/4), benign
specificity 100 % (3/3), 0 errors, over seven real applications.

| # | Finding | Resolution |
|---|---|---|
| 1 | **"Precision 100 %" from one flagged sample is compatible with 21 %.** The harness printed a point estimate and the number read as a result | Wilson 95 % intervals and denominators are now part of the metrics and the CLI output, and a note fires when precision rests on fewer than ten flagged samples |
| 2 | **Recall 25 % is a coverage gap, not a detection failure.** All three MASTG crackmes expose exactly one component and it is the launcher, which RECON excludes as a candidate — so the pipeline never looked | Documented in `BENCHMARK_RESULTS.md §4`. The fix is new gates (in-code secrets, insecure storage), **not** relabelling the corpus. A mixed-class corpus will always depress recall against a single gate |
| 3 | The true positive is narrower than it looks: exported `ViewStatement.onCreate` → `WebView` loader with no permission and no caller check, and **no data flow**, so it does not establish that attacker input reaches the URL | Stated in the report, in §3 of the results file, and in R-21 |
| 4 | `a2dp-volume` was neither flagged nor clean: one exported receiver (`a2dp.Vol.Widget`) has no lifecycle entry point, so reachability was never established | Counted as `manual_review`, not a false positive — silence and safety are different results, which is the pattern this project keeps having to enforce |
| 5 | The committed manifest and the fetched manifest have different shapes (`file` + `url` vs `apk_path`), and the loader only understood one | `load_corpus` accepts both; a manifest test asserts every sample pins a 64-hex SHA-256, states the basis of its label, and that the corpus contains both labels |

**What is now proven.** The pipeline confirmed one finding on a real published vulnerable app
with all four gate clauses evidenced, confirmed nothing on three benign apps, and the whole thing
reproduces from pinned inputs in two commands.

**What is emphatically not proven.** That precision is high. Seven samples, labelled by the
person who wrote the detector, with one flagged positive, cannot establish a rate. The results
document says so in §6 and §8, and `IMPLEMENTATION_STATUS.md` keeps the claims-audit row for
"reduces false positives" closed.

## 2026-11-15 · RL-008 · The report found a contradiction the tests had not

**Scope:** ARCHIVIST (report), War Room UI, `GET /scans`, benchmark harness. Tests 264 → 301.

| # | Finding | Resolution |
|---|---|---|
| 1 | **A stored verdict contradicted its own rationale.** The finding read `rejected / not-reachable` while the rationale in the same row said "could not be decided: no evidence for caller_check_absent". `_rationale` tested missing evidence before decisive failure, the reverse of the decision order | Rationale follows the decision: decisive failure is described as a refutation, and unestablished clauses are admitted alongside it. Found by reading a generated report, not by a failing test - every test asserted the verdict, none asserted the sentence |
| 2 | The report listed itself in its own evidence index, so every write changed the document and the content hash could never deduplicate | Reports are excluded from the evidence index; `report_written` is excluded from the event summary. A document is not a source for itself |
| 3 | The report's header pointed at §8 for the evidence index, which is §7 | Corrected; the section numbers are asserted by test against the rendered headings |
| 4 | The War Room's event panel listened for a hardcoded list of event names, so any event type it did not know about would silently not appear | The panel replays `GET /scans/{id}/events`, then follows the stream. A UI that filters by omission is a UI making claims |
| 5 | Writing a report appends events, so a second write legitimately produces a different document. An earlier test asserted byte-identical rewrites | The test now asserts what is true: two writes are two documents, each announced once, and `latest` returns the newer one |
| 6 | **The report described a scan that was still running.** It was written inside `REPORTING`, so the document said `Final state: REPORTING` and `Stop reason: not recorded` - in the one artefact a reader keeps | Written after the transition to `CLOSED`, when both fields are final. Found by reading the live report, not by a test: the test asserted `state == CLOSED` on the *response*, which was correct, while the document disagreed |
| 7 | Rejected findings carried no `component_ref`, so a report table had an empty column where the component should be | SPECTRE passes the component; the contract already had the field |

Finding 1 is the one to keep. It was invisible to 300 passing tests because the tests checked
the *verdict* and the *status*, and the contradiction lived in a free-text field that only a
reader of the report would see. The lesson is narrow and worth recording: whenever a decision and
its justification are stored separately, something must check that they agree.

**What is proven now.** A real APK produces a 4.6 KB Markdown report with eight sections and a final state of `CLOSED` / `completed`, an
evidence index of hashes, and a "not determined" section that names what was left open; the War
Room serves that scan list and those findings from `/api/v1` alone; and the benchmark harness
drives the real pipeline end to end (upload → RECON → NEXUS) and reports `measured: false` when
it has no corpus.

**Still unproven.** No labelled corpus exists, so **precision and recall are unmeasured** - the
harness is machinery without samples. No true positive on real code. The UI has no browser test
(no Playwright in this environment), so its rendering is asserted at the HTML level only, not by
clicking it. No model, no dynamic analysis, no Postgres trigger.

## 2026-11-15 · RL-007 · NEXUS — the FSM and the scorer caught two of the three bugs

**Scope:** frontier-driven dispatch loop, `POST /scans/{id}/nexus`, `services/state.py`.
Tests 243 → 264.

| # | Finding | Resolution |
|---|---|---|
| 1 | The loop's first close-out path went `SELECTING -> VALIDATING`, which the FSM does not permit. The state machine **refused to run** rather than putting the investigation in an unreachable combination | Close-out leaves through `OBSERVING -> VALIDATING`, the only edge into it. The FSM catching a design error at runtime is the point of ADR-003 |
| 2 | **Dispatch order was not deterministic.** Ties in the scorer broke on the entry id, and ids are ULIDs - clock plus randomness - so two runs of the same APK dispatched the same candidates in a different order | Tie-break on depth, then action and target (properties of the artefact), then id. Regression test orders the same frontier with deliberately swapped ids |
| 3 | **A truncated index could still produce a `confirmed` finding.** Truncation only downgraded `not-reached`; when the sink *was* reached, `caller_check_absent: true` survived and the gate confirmed | A found path proves its own methods, but a truncated graph cannot rule out a guard in a caller that never made it into it. `caller_check_absent` is `None` on an incomplete index |
| 4 | NEXUS drove SPECTRE's analysis but never emitted `code_analysis_complete`, so a stream client waiting for that marker would hang until the scan closed | NEXUS emits it when it dispatched work, and not when it did not - an "analysis complete" event for analysis that never ran would be a false statement |
| 5 | A PHANTOM entry at passive intensity reported "PHANTOM is not implemented" and hid the fact that the action was forbidden at this intensity regardless | The intensity gate reports first: it is the constraint an analyst could change. Both reasons are true; the decisive one is stated |

Finding 2 is the one worth keeping. The determinism requirement had been tested *within* one
run (rank twice, same answer) and had passed for months. It took a test that ran two separate
investigations and compared their dispatch orders to show the ordering was a function of the
clock. Determinism across runs and determinism within a run are different claims.

**What is proven now.** A real APK (`com.politedroid_4.apk`) goes upload → RECON → NEXUS →
`CLOSED` over HTTP: 1 candidate dispatched, 1 rejected, `stop_reason: completed`, budget 1 of
20 used, and the same scan repeated produced an identical decision payload, step list and
result set.

**Still unproven.** The loop cannot create work: it dispatches what RECON queued and nothing
else, so "autonomous investigation" remains unearned prose. No model is called, no re-planning
happens, PHANTOM/VECTOR/ORACLE are dropped with reasons, and ARCHIVIST writes no report - the
investigation closes with events and findings only, which the API response says in its `notes`.

## 2026-11-13 · RL-006 · SPECTRE — the real APK found five bugs the fixtures hid

**Scope:** dex indexing, call graph, reachability search, SPECTRE service, `POST
/scans/{id}/spectre`. Tests 176 → 243 (6 skipped, Postgres-only).

Every finding below came from running the pipeline against a real APK
(`com.politedroid_4.apk`, 18 489 bytes) or from a test that contradicted an assumption — not
from review. The synthetic fixtures passed throughout; four of these bugs were invisible to
them.

| # | Finding | Resolution |
|---|---|---|
| 1 | A guard on the caller (`checkCallingPermission` and friends) was mapped to `not-reachable`, telling the analyst "there is no path" when the truth was "there is a path and it is checked" | New reason `guarded-by-caller-check`. A guard refutes `caller_check_absent`; it says nothing about reachability |
| 2 | The call graph contained only methods that had internal callees, so lifecycle methods with no in-app callees were simply absent — the entry point of the only candidate did not exist in the graph | Every method is seeded as a node; `internal_calls` counts edges separately from `graph_nodes` |
| 3 | Entry points were matched by `MethodRef(class, name)` with an **empty descriptor**, so real `onReceive(Context,Intent)V` never matched and the app reported `no-entry-point` | `CallGraph.methods_named()` matches by name and returns the overloads |
| 4 | A `None` clause value counted as a failed clause, so a candidate the tool had never refuted came out `rejected` — an absence of evidence reported as evidence of absence | `Clause.absence_is_evidence` + `GateResult.failed_decisively`; decisive failure is checked before missing, so `None` yields `insufficient_evidence` |
| 5 | **A false positive.** With the graph finally working, the real APK produced `confirmed`: exported receiver → `SharedPreferences.getString` → "shared-prefs" sink | The sink was not a sink. Reading a preference discloses nothing; reachability without data flow cannot tell that from exfiltration. `shared-prefs` and `intent-redirect` removed from the catalogue, with a regression test asserting they stay out |

| 6 | A complete search that reached **nothing** reported `caller_check_absent: true` and `path_length: 0` — a claim about a call chain that does not exist, reading as "the entry point is the sink" | Both are `null` when there is no path. Only a reached path can say anything about the checks on it |
| 7 | Stored `gate_evidence` collapsed the tri-state to booleans, so a clause nothing had been offered as evidence about was stored as `false`, indistinguishable from "refuted" | `as_gate_evidence()` emits `null` for never-established; `Finding.gate_evidence` and `VerdictRecord.gate_detail` accept the third state |
| 8 | The finding title said "reachability not established" on a finding whose verdict was a *decisive* refutation | The title now follows the verdict: "no sensitive sink reachable in the application code" |

Findings 6–8 were all found by reading the JSON of a live `curl` run rather than by a test —
the stored record disagreed with what the pipeline had actually established. Finding 5 is the
one worth keeping: the pipeline's first confirmed finding on real code was
wrong, and it was wrong because the catalogue was written by enumeration rather than by a
rule. The rule now stated in `sinks.py` is that a sink must be an operation whose *execution*
is security-relevant. After the tightening the same APK is correctly `not-reached` →
`REJECTED` over a complete traversal of six methods.

**What is proven now.** A real APK, parsed by real androguard, yields a real graph (10
classes, 34 methods, 41 internal calls) and a deterministic verdict. Truncation is never
refutation, asserted by test. The gate can reject on exhaustive absence.

**Still unproven.** No confirmed true positive on real code — the corpus has no app with the
pattern, so every "confirmed" verdict so far comes from synthetic dex. No multi-dex, no
obfuscated app, no reflection, no data flow. JADX-level understanding of the reachable
methods is not attempted. The Postgres trigger remains unexecuted.

**Scope:** binary manifest decoding, surface derivation, RECON service, SSE stream. Tests

| # | Finding | Resolution |
|---|---|---|
